## vsDriverbox「转发」术语澄清（架构梳理，无代码改动）

项目里有**两条都叫"转发"的链路**，必须区分：

- **通道 A｜Printer.py（prn 传输层）** —— 用户口中的"转发"。
  监听 9111（TCP/IP）或热文件夹收 NS/RIP 出来的 PRN → 剥 48 字节头
  （`HEADER_BYTE_SIZE=48`；`if self.index == 1` 才发头，且用 `_set_header`
  按 `print_length` 改写 height），其余只发 body → 转发到打印机 9100。
  与拼接、与 834 完全无关。

- **通道 B｜Camera.py + StreamRealtime.py（图像生成层）** —— 即"实时转发路径"。
  线扫帧 + Modbus（`y_axis_pos()` / `x_axis_pos()`）→ 拼接 → 带(band) →
  `data_socket` 发到 `data_recv_addr:data_recv_port`（默认 127.0.0.1:9120，
  接收端 `drivers/camera/CamSrv.py`）。头为 28B struct `<IIIIId`
  = MAGI / total / width / height / dataSize / y_step(double)。
  StreamRealtime 只替换了这一段的拼接引擎，带的几何口径不变。

## 834 的准确含义

- 834 = **带(band)的图像高度（像素行数）**，同时就是随带外发的 `y_step`。
- 来源：`forward = round((Step - StepCopy) / K_Coef)`，`Step = modbus.y_axis_pos()`
  （单位 0.0001mm，`y_axis_pos()` 返回 `YaxisPosition*10000`）。
  `K_Coef = (25.4/DPI)*10000`，DPI=300 → 846.67；834px ÷ 11.811px/mm = 70.61mm，
  与单帧步进 70.626mm 吻合。
- **注意区分**：这是驱动盒**带流**的高度，不是 PRN 头里的 height 字段
  （后者由 RIP 生成、或被 `_set_header` 按 print_length 改写）。
- 834 只是匀速名义值；逐带真实高度仍由各帧 Step 差决定（f_k），
  这正是"纵向相位绑旧口径"限制的来源（T→F 828.7 / F→T 840.3）。

## README §6 三个"已知遗留"的核实结果（只读排查，未改代码）

### ① export_calib_img 复选框无效 —— 比 README 说的更彻底

- 链路本身是通的：`Camera.__init__(export_calib_img=...)` → `ImageStitch(...)`（Camera.py:166）
  → `self.__export_calib_img`（1041）→ `stitch_from_json()` 里用（1371）。
- **断点 1**：`main.py` 的 `create_camera_instance` 压根没传这个 kwarg（全库 grep 无命中）→ 恒为 False。
- **断点 2（关键）**：唯一消费它的 `Camera.stitch_from_json()`，**全项目已无生产调用点**
  （只剩 `testdata/eval_stitch.py`、`testdata/tools/compare_stitchers.py`、
  `_diag/run_old_stitcher_20260627.py` 这些开发脚本在用）。
  托盘「离线拼接」早已改走 `StreamStitch.run_stream_stitch()`（main.py:465）。
- **结论**：只补 main.py 那个 kwarg 没用，复选框依然是死的。要么删掉它，
  要么在新拼接路径里重新实现导出 —— **需要产品决策**。

### ② 导入配置时下拉框不联动 —— 确认，且发现更严重的语言耦合

- `load_ui_data()`（窗口初始化，config.py:647-666）**有**处理：Combobox 用 `.set(value)`
  并手动触发 `_on_forward_mode_change` / `_on_listen_mode_change`。✓
- `import_config()`（config.py:620-632）**没有**：走 else 分支做
  `delete(0, END)` + `insert(0, str(value))` —— 对 `state="readonly"` 的 Combobox
  本就是错误用法，且完全没触发联动回调。**这就是 README 描述的现象。**
- **额外发现（README 没提，更严重）**：`_on_listen_mode_change`（config.py:387）
  硬编码比较 `mode == "热文件夹"`；而 `config_ui.hot_folder` 三语言分别是
  `热文件夹 / Hot Folder / Thư mục nóng`（translations.yaml:40/171/302）。
  → 切到英文/越南语界面后，监听方式的联动直接失效。
- 更糟的是后端也硬编码：`Printer.start()`（Printer.py:182/198）判断
  `if self.listen_mode == "TCP/IP" ... elif self.listen_mode == "热文件夹"`。
  而配置里存的是**下拉框显示的本地化字符串**（main.py:280 直接透传）。
  → EN 界面下存进 `.syscfg` 的是 `"Hot Folder"`，两个分支都不匹配，
  **监听线程一个都不启动，但 `start()` 仍返回 True** —— 静默失败：
  界面显示已启动，实际什么都没监听。现场目前跑 zh_CN，所以一直没暴露。
- `forward_mode` 不受影响（`options.hs_dll` 三语言都是 `"HS DLL"`，语言无关）。
- 修法建议（沿用 README §5 里 `cal_sel` 已用过的那套思路）：改成语言无关 token；
  最小改动是加一个"识别全部拼写"的集合常量
  （`{"热文件夹", "Hot Folder", "Thư mục nóng"}`），config.py 与 Printer.py 共用，
  无需迁移已有 `.syscfg`。

### ③ stitch_timeout 未生效 —— 确认，且是彻底失效

- `stitch_timeout` 全库仅 4 处：main.py:220 传入 → `Camera.__init__`（63）
  → `self.__stitch_timeout`（125）→ `get_stitch_timeout()`（259/261）。
- **`get_stitch_timeout()` 没有任何调用方**；`utils/mp_helper.py` 里
  `ProcessProxy.__getattr__` 的 wrapper 用的是自己的缺省 `timeout=10.0`。
- `StreamStitch.run_stream_stitch()`（StreamStitch.py:117-124）签名里**没有** timeout 参数。
- **结论**：README 说它"被当作进程通信超时使用"也不准确 —— 它现在是个纯死旋钮。
  要么接进流式拼接，要么把界面这一项去掉 —— **需要产品决策**。
