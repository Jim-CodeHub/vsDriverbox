## 现场测试报错：Modbus 读寄存器崩溃（1.1.2_Beta_03）

日志 `log/20260912_100805.log` 关键行：

```
Camera: Camera frame started [0]
Camera ERROR: Camera abnormal stop: Modbus thread exception:
  ModbusClientMixin.read_holding_registers() got an unexpected keyword argument 'slave'
```

### 根因

- **pymodbus API 改名**：`slave=` → `device_id=`（3.14 起旧名彻底移除）。
  数字花样的打包环境 `digitalpainter` 装的是 **pymodbus 3.14.0**；
  `1.1.2_Beta_02` 是在别的机器/旧版本上打的，所以以前没炸。
- 崩溃点在相机收到**第一帧**时（Modbus 线程才第一次去读寄存器），
  所以启动阶段一切正常、看起来像"启动成功"，很有迷惑性。
- 实测确认 3.14 其余 API 都没变：`count=` / `client.convert_from_registers()` /
  `client.DATATYPE.FLOAT32` / 响应的 `.isError()` `.registers` 全部照旧，
  **只有 `slave` 这个参数名变了**。

### 修复（drivers/camera/Camera.py）

- 模块级解析一次参数名，新旧 pymodbus 通吃（防止以后在别的机器、旧版本上反向下炸）：
  ```python
  def _modbus_id_kwarg() -> dict:
      try:
          import inspect
          params = inspect.signature(
              ModbusTcpClient.read_holding_registers).parameters
          return {"device_id": 0} if "device_id" in params else {"slave": 0}
      except Exception:
          return {"device_id": 0}   # 兜底按 3.14 的写法，别退回 slave=
  _MODBUS_ID = _modbus_id_kwarg()
  ```
- 三处 `slave=0` 改为 `**_MODBUS_ID`：
  - `write_registers(192, values=..., slave=0)`（send_pause）
  - `read_holding_registers(180, count=4, slave=0)`（X/Y 轴位置）
  - `read_holding_registers(190, count=1, slave=0)`（机器状态）

### 验证方式（无需真实板卡）

写了 `_diag/mock_modbus_server.py`：本地起 pymodbus 模拟 TCP 板卡
（180-183 = 两个 FLOAT32，190 = 状态位，192 = 暂停寄存器），
直接用**真实的 `Camera.VisionModbus`** 跑完整链路，全过：

- `_MODBUS_ID` 解析为 `{'device_id': 0}`
- `get_info()` → X=1.25, Y=-2.5；`x_axis_pos()`=12500, `y_axis_pos()`=-25000
- 状态位：print=1 / direction=1 / emergency=0 / trigger=0
- `send_pause(True)` → 寄存器 192 写回 0x8000

**踩坑记录**：pymodbus 3.14 的 `ModbusSequentialDataBlock(180, values)` 内部
起始地址存成 `address-1`，客户端地址 A 取 `values[A-start+1]`。
要让客户端 180 读到 `values[0]`，start 必须写 **181**（差一位）。
另外 3.14 的 `ModbusSlaveContext` 已改名为 `ModbusDeviceContext`，
构造参数是 `hr=`/`co=`/`di=`/`ir=`（不是 `holding_registers=`）。

## 附带发现：异常停机时那两条 "Other errors" 是重复调用 stop() 造成的噪音

日志 `20260912_100805.log` 里还有两条看着吓人的报错：

```
24.383 Camera ERROR: Failed to stop acquisition: Other errors
24.383 Camera ERROR: Failed to destroy stream: Other errors
```

### 结论：无害噪音，但会误导现场排障

证据（看时间戳就能坐实）——`stop()` 被调了两次：

1. **第一次**（24.081 起）：`__Mb_Thread` 捕获 Modbus 异常后自己调了 `self.stop(reason)`。
   这一轮**完整成功**：24.081 "Camera stream ended" → "Disconnected from data server"
   → 24.193 "Camera driver service stopped completely"，中间没有任何 Failed 行。
2. **第二次**（24.383 起）：主进程 `stop_system()` → `camera_instance.stop()` 又来一遍。
   此时流已停、句柄已释放 → `ItkStreamStop` / `ItkDevFreeStream` 对着无效句柄调用，
   双双报错，被 `try/except` 吞掉（返回 `success=False`，但 main.py 不检查返回值）。

所以相机其实**已经正常释放**，只是日志里留下两条假的"停止失败"。
根因是 `Camera.stop()` **没有幂等保护**。

### 建议的最小改动（未实施，等 Beta_04 验证完再进下一版）

```python
def stop(self, reason=None):
    if self.__stopped:          # 新增：幂等，内部线程和主进程都会调 stop()
        return True, None
    self.__stopped = True
    ...
```
（`__stopped` 在 `__init__` 里初始化为 False）

### 顺带：错误码丢了，不利于排障

`Camera.ItkCAMError.__init__`：`self.string = self._ERROR_MAP.get(value, "Other errors")`
——**未映射的错误码不带数值**，日志里只剩一句 "Other errors"，看不出到底哪个码。
建议改成 `f"Other errors (code=0x{value:08X})"`，一行的事，现场排障省很多。

（两条改动都很小；为保持 Beta_04 的源码/产物一致，本轮都没动代码。）

## 现场第二次报错：strip 1 outside the y margin（扫描不出图 → 上位软件收不到）

日志 `log/20260912_143029.log`、`20260912_143300.log`（两次几乎一样，可稳定复现）：

```
Camera ERROR: Camera abnormal stop: Stitch thread exception:
strip 1 needs rows [-270, 30515) outside the y margin; the placement model is probably wrong
```

现象：系统能启动、相机能出帧（frame 0..5），但拼接线程一崩 → 一条带都不发
→ 上位软件（127.0.0.1:9120）收不到任何图像，现场就说"扫描不出东西"。
Modbus 修复已生效（Step/MSP 都正常读到）。

### 复现（按 master 指定用 testdata/20260903/calib）

`_diag/repro_y_margin.py`：同一批 20260903 图像，喂两组 MSP 对照——

| 用例 | 结果 |
|---|---|
| A) 数据集原始 MSP | 8 带，形状 (834, 21259)，y_step 834 ✓ |
| B) 现场日志 MSP | `strip 1 needs rows [-271, 30514)` ✗ 与现场一致 |

**关键差异**：现场 MSP 比数据集整体高 **+499,880 单位（≈590 px）**
（Step 完全相同，说明是同一台机器同一扫描程序，但 **X 轴零点漂了**）。
注意：`validate_rt.py` 里 20260903 用的 `x_base_L=2461080 / x_base_R=29191669`
对应的是数据集的 MSP（2,461,260 / 29,191,689），现场已变成 2,961,140 / 29,761,011。

### 根因（`_diag/diag_msp_repair.py` 插桩实测）

y 摆放公式（`_place`）：
```
direction=True : raw_y = -MSP/D_MSP_Y - corrected_height + Y_OFFSET_TRUE_PX
direction=False: raw_y = -MSP/D_MSP_Y                     + Y_OFFSET_FALSE_PX
```
- **`D_MSP_Y / Y_OFFSET_*_PX` 都没有被 StreamRealtime 注入**（实时路径只注入了
  `D_STEP_X`、`X_OFFSET_FALSE_PX`、seam_inset），恒用模块缺省。
- 摆放用的是**绝对 MSP**，没有减机器 X 零点 → X 原点一漂，整批条带一起移动。
- strip 0 的 MSP=0 会被 `infer_standard_msp_causal` 修复（实测修复是对的：
  数据集 → 2,461,400；现场 → 2,960,890，都与同方向其它条带吻合），
  但随后 `special_offset = standard_msp/D_MSP_Y + ZERO_MSP_FINE_TUNE_PX`
  又把它**按 MSP=0 定位**，导致 strip 0 与其余条带天然差约 2908 px（True 向）
  / 3693 px（False 向）。
- 因此 **Y_MARGIN=4096 时实际只剩约 400 px 余量**（实测 strip 1 落在 row=+322）。
  现场 X 零点 +590 px → row=-271 → 越界停机。

### 修复

`stitch_stream_final.py`：`Y_MARGIN = 4096` → **`8192`**（含详细注释说明来龙去脉）。

`_diag/test_y_margin_fix.py` / `verify_fix.py` 验证：
- **无害**：数据集在 4096 与 8192 下产出的带**逐字节相同**（摆放与缝质量不变）
- **有效**：现场 MSP @8192 → 8 带，形状 (834, 21259)，y_step 834
- 内存代价：buffer 高 38,977 → 47,169 行，约 +70 MB（335 → 405 MB）
- 可容忍的 X 零点漂移：约 4,500 px ≈ 380 mm
